# uploader.jp 魚拓作戦 — システム設計書

- **文書バージョン:** 1.4
- **ステータス:** MVP-3分散配置・余剰レプリカ整理の実装判断反映
- **目的:** uploader.jp の終了に備え、MMD関連ファイルとそのメタデータを、権利・公開条件を区別しながら長期保全する。

## 1. 概要

本プロジェクトは、uploader.jp 上で公開・配布されている MMD 関連ファイル（モデル、モーション、エフェクト、ツール、アクセサリ等）について、作品情報・元URL・作者情報・利用規約などのメタデータと、ファイル本体を保全するためのシステムを構築する。

保全と一般公開は別の機能として扱う。ファイルを保全対象として記録・保存していても、権利情報や許諾が確認できない場合は、一般ユーザー向けにダウンロード提供しない。

### 1.1 設計上の基本方針

1. **保全と再配布を分離する。** 保存できることと、一般公開できることを同一の判定にしない。
2. **メタデータは可能な限り記録する。** 再配布不可・不明のファイルも、記録対象から自動的に除外しない。
3. **メタデータ管理とファイル本体の保存を分離する。**
4. **全ノードへ全データを複製しない。** ファイル単位で保存先ノードを割り当てる。
5. **中央管理サービスを制御点とする。** 検索、権限判定、保存タスク、配信を中央で管理する。
6. **保存ノードを一般ユーザーへ直接公開しない。** ユーザー向けアクセスは中央の API／配信ゲートウェイを経由させる。
7. **初期版は単純な構成を優先する。** 独自 P2P プロトコルやファイル断片化は初期版では実装しない。

## 2. 対象範囲

### 2.1 対象データ

- MMD モデル
- モーション、カメラモーション
- エフェクト、シェーダー
- アクセサリ、ステージ
- MMD 関連ツール
- 配布物に付随する説明文、readme、利用規約
- 元ページ、元URL、作者名、公開日時などのメタデータ

### 2.2 初期版の対象機能

- 作品・ファイルの目録登録
- メタデータ検索
- `uploader.jp` を取得元とするファイル取得ワークフロー
- SHA-256 による完全性検証
- ファイルごとに最低 2 ノードへの分散配置
- 権利・公開ポリシーの管理
- RBAC による管理者・確認担当者の権限分離
- 削除・公開停止申請フォーム
- 外部公開情報の提供フォームと確認後のリダイレクト設定
- 条件を満たすファイルのみの中央経由配信
- OpenTelemetry 等によるテレメトリ収集と Grafana での可視化
- 操作履歴と障害の記録

### 2.3 初期版では実装しないもの

- 独自の完全分散型 P2P プロトコル
- 全ファイルの全ノードへの複製
- ファイルの細かなチャンク分割・再構成
- 権利状態が不明なファイルの自動公開
- 保存ノードから一般ユーザーへの直接配信

## 3. システム構成

```text
                    ┌─────────────────────────┐
                    │      一般ユーザー       │
                    └────────────┬────────────┘
                                 │ HTTPS
                    ┌────────────▼────────────┐
                    │ Web UI / API / 配信GW   │
                    │ 検索・認可・配信制御    │
                    └──────┬──────────┬───────┘
                           │          │
                 ┌─────────▼───┐  ┌───▼────────────┐
                 │ PostgreSQL  │  │ 管理・タスク制御│
                 │ メタデータ  │  │ 保存配置・監査  │
                 └─────────────┘  └───┬────────────┘
                                      │ HTTPS / mTLS
                    ┌─────────────────┼─────────────────┐
                    │                 │                 │
              ┌─────▼─────┐     ┌─────▼─────┐     ┌─────▼─────┐
              │ 保存ノードA│     │ 保存ノードB│     │ 保存ノードC│
              │ VPS / NAS  │     │ PC / NAS   │     │ VPS / NAS  │
              └───────────┘     └───────────┘     └───────────┘
```

### 3.1 中央サービス

中央サービスが担当する機能：

- Web UI と API
- メタデータ検索・表示
- 保存タスクの作成と配布
- ノードの登録、状態監視、容量管理
- ファイルの配置状況の管理
- 公開可否の判定
- ユーザー向けダウンロード配信
- 操作・権限変更・配信の監査ログ

中央管理サービスは設計上、稼働を継続する前提とする。ただし、運用上の事故に備えて、DB・設定・監査ログのバックアップは行う。

### 3.2 保存ノード

保存ノードはファイル本体を保管する。ノードは中央サービスへアウトバウンド接続し、タスク取得・状態報告を行う。インターネット上にノードのストレージを直接公開しない。

ノードの種類：

- **A ノード:** 運営・協力者が管理する VPS、サーバー、NAS
- **B ノード:** 一般参加者が管理する PC、NAS、サーバー

A/B の混合構成とし、保存先はファイル単位で割り当てる。すべてのノードにすべてのファイルを複製する構成にはしない。

## 4. 主なワークフロー

### 4.1 目録登録・取得元

1. ファイルの取得元は `uploader.jp` とする。
2. 管理者がアカウントを作成し、管理画面から作品・ファイル情報を登録する。
3. 作者、元ページURL、ファイル名、README 等の説明資料、利用規約や権利情報を記録する。
4. README 等が存在しない、または権利・再配布条件を確認できない場合は、定められた連絡手順で確認を依頼する。
5. 権利状態が確認できていないファイルは、保存状態とは独立して一般向け配信を不可とする。
6. 取得・保存ができない場合は、その理由と確認日時を記録する。

取得手段は、対象サイトの利用条件、技術的制約、適用される権利関係を確認したうえで実装する。

### 4.2 保存タスク

1. 中央サービスが保存対象ファイルと保存先ノードを決定する。
2. ファイルごとに最低 2 つの正常な保存先を確保する。
3. ノードエージェントが認証済み接続でタスクを取得する。
4. ファイルを取得または受領し、指定ストレージに保存する。
5. SHA-256 ハッシュとサイズを計算する。
6. 中央サービスが期待値と照合し、保存状態を更新する。
7. 失敗時はエラーを記録し、自動試行は1実行あたり最大5回とする。
8. `failed` の保存タスクは管理者が手動再実行できる。再実行時は試行カウンタを0に戻し、新たに最大5回を許可する。再実行操作と各試行結果は監査ログに残す。
9. 再実行前にステージング元データのサイズとSHA-256を再検証する。元データが欠損・破損している場合は、管理者が正しいファイルを再アップロードできる。
10. ノードは再試行前に未検証の保存実体と残存する部分ファイルを清掃する。SHA-256とサイズの検証成功後に限り `verified` にする。失敗中は再実行用のステージング元データを保持し、成功時に削除する。
11. ノードの離脱や故障で保存先が 2 未満になった場合、再配置タスクを作成し、稼働中のノードで最低 2 保存先への復旧を目指す。

### 4.3 一般ユーザーへの配信

1. ユーザーが中央 Web UI でファイルを検索する。
2. API が公開ポリシーとファイル状態を確認する。
3. 公開条件をすべて満たす場合だけ、配信ゲートウェイがファイルを取得する。
4. ユーザーには中央サービス経由で配信する。
5. 配信結果を監査ログに記録する。

保存ノードのアドレスや認証情報は、一般ユーザーへ返さない。

### 4.4 削除・公開停止申請

1. ユーザーが専用フォームから削除または公開停止を申請する。
2. 申請を受け付けた時点で受付記録を作成し、確認担当者が速やかに確認できる状態にする。
3. 公開停止が必要と判断された場合は、中央配信を停止する。
4. 削除が必要と判断された場合は、対象ノードへの削除タスクを作成し、完了状況を追跡する。
5. 対応者、判断理由、対応時刻、対象ファイル、各ノードの処理結果を記録する。

「即時対応」は申請受付と確認開始を速やかに行う要件とし、権利判断や各ノードでの削除完了までの時間は監視・記録する。

### 4.5 外部公開情報の提供

1. ユーザーが、同じファイルが他所で公開されていることを示す情報を専用フォームから提供する。
2. 確認担当者が URL や根拠情報を確認する。
3. 情報が確認できた場合、対象ページを外部の公開先へリダイレクトする設定を行う。
4. 対象ファイルについてノード削除タスクを作成し、可能なノードからデータを抹消する。
5. リダイレクト設定と削除処理は別の状態として管理し、各処理の結果を監査ログへ記録する。

## 5. 権利・公開ポリシー

保存状態と公開可否は、別々の属性として管理する。

### 5.1 主要な属性

- `preservation_status`: ファイル本体の保全状態
- `redistribution_policy`: 再配布に関する判定
- `public_download_enabled`: 一般向けダウンロードを許可する管理フラグ

`preservation_status` の例：

- `uncollected` — 未取得
- `queued` — 保存待ち
- `stored` — 保存済み
- `verified` — ハッシュ等の検証済み
- `degraded` — 保存先不足・一部欠損
- `missing` — 保存実体を確認できない
- `error` — エラー

`redistribution_policy` の例：

- `allowed` — 公開・再配布可能と確認済み
- `restricted` — 条件付き、または再配布不可
- `in_progress` - 確認中
- `unknown` — 未確認

### 5.2 公開判定

一般向けダウンロードは、少なくとも次の条件をすべて満たす場合に限る。

```text
public_download_enabled == true
AND redistribution_policy == "allowed"
AND preservation_status == "verified"
AND at_least_one_healthy_placement == true
```

条件を満たさない場合は、ファイル本体を配信せず、必要に応じてメタデータのみを表示する。権利情報が不明なファイルは、確認が済むまで公開不可として扱う。

### 5.3 ポリシー変更

- 公開可否の変更者、変更日時、変更理由を記録する。
- 公開停止時は、新規ダウンロードを直ちに拒否する。
- 将来キャッシュを導入した場合、公開停止やポリシー変更に合わせてキャッシュを失効させる。
- ファイル本体の保存状態を変更しても、再配布ポリシーを自動変更しない。

> 技術的にファイルへアクセスできることと、保存・複製・転送・一般配布の権限があることは別々に管理する。

## 6. データモデル案

### 6.1 `Artifact` — 作品・配布ページ

| フィールド     | 説明             |
| -------------- | ---------------- |
| `id`           | 内部ID           |
| `title`        | 作品名           |
| `creator_name` | 作者名・配布者名 |
| `source_url`   | 元ページURL      |
| `description`  | 説明文           |
| `created_at`   | 登録日時         |
| `updated_at`   | 更新日時         |

### 6.2 `FileObject` — ファイル本体の論理レコード

| フィールド                | 説明                       |
| ------------------------- | -------------------------- |
| `id`                      | 内部ID                     |
| `artifact_id`             | 関連する作品ID             |
| `original_filename`       | 元ファイル名               |

| `sha256`                  | SHA-256 ハッシュ           |
| `media_type`              | MIMEタイプ等               |
| `preservation_status`     | 保全状態                   |
| `redistribution_policy`   | 再配布ポリシー             |
| `representative`          | 再配布ポリシー確認担当者ID |
| `public_download_enabled` | 一般配信の管理フラグ       |

### 6.3 `Policy` — 権利・公開条件

| フィールド       | 説明                   |
| ---------------- | ---------------------- |
| `id`             | 内部ID                 |
| `file_object_id` | 対象ファイルID         |
| `policy_type`    | 許諾・禁止・不明など   |
| `evidence_url`   | 根拠となる規約・ページ |
| `evidence_note`  | 根拠の要約             |
| `checked_at`     | 確認日時               |
| `checked_by`     | 確認担当者             |

### 6.4 `Node` — 保存ノード

| フィールド       | 説明                           |

| `last_seen_at`   | 最終応答日時                   |
| `agent_version`  | エージェントのバージョン       |

### 6.5 `Placement` — ファイルと保存ノードの対応

| フィールド       | 説明                                    |
| ---------------- | --------------------------------------- |
| `id`             | 配置ID                                  |
| `file_object_id` | ファイルID                              |
| `node_id`        | 保存ノードID                            |
| `storage_key`    | ノード内の内部保存キー                  |
| `sha256`         | 保存実体のハッシュ                      |
| `status`         | queued / stored / verified / missing 等 |
| `verified_at`    | 最終検証日時                            |

### 6.6 `Task` — 保存・検証タスク

| フィールド       | 説明                                     |
| ---------------- | ---------------------------------------- |
| `id`             | タスクID                                 |
| `task_type`      | ingest / verify / replicate / restore 等 |
| `file_object_id` | 対象ファイルID                           |
| `source_node_id` | 取得元ノード（任意）                     |
| `target_node_id` | 保存先ノード（任意）                     |
| `status`         | queued / running / succeeded / failed    |
| `priority`       | 優先順位 (0-5)                           |
| `attempt_count`  | 現在の実行サイクルにおける試行回数（最大5回。管理者の再実行時に0へリセット） |
| `last_error`     | 最後のエラー                             |
| `created_at`     | 作成日時                                 |
| `updated_at`     | 更新日時                                 |

### 6.8 `FileReplicationSettings` — ファイル単位の複製設定

| フィールド | 説明 |
| --- | --- |
| `file_object_id` | 対象ファイルID（主キー） |
| `desired_replica_count` | 確保したい最低複製数。既定値は2 |
| `priority` | 複製タスクの優先度（0–5） |
| `updated_at` | 設定更新日時 |

複製数はファイルごとに設定し、保存容量全体に固定上限は設けない。複製数を減らしても、既存の余分な複製を自動削除しない。

### 6.7 `AuditLog` — 監査ログ

権限変更、公開・非公開切替、ファイル取得、配信、ノード登録、管理操作などを記録する。ログには時刻、実行主体、対象、操作、結果、理由を含める。

## 7. ノード配置・冗長化

### 7.1 基本配置

- 全ノードへ全ファイルを複製しない。
- ファイルごとに必要容量、ノードの空き容量、稼働状態を考慮して保存先を決める。
- ノードの停止や離脱を想定し、配置情報と実際の状態を定期的に照合する。
- 同一ファイルを追加複製する場合は、優先度・容量・ポリシーを確認してタスク化する。

### 7.2 優先的な追加複製

重要度が高いファイルや、唯一の保存先しかないファイルについて、運営判断で追加複製を行える設計にする。複製数は設定値として管理し、初期段階で一律の値を固定しない。

### 7.3 整合性検証

- SHA-256 を用いてファイルの同一性を確認する。
- 定期検証と、保存・転送直後の検証を分ける。
- 不一致時は公開配信を停止し、再取得・別ノードからの復元を試みる。
- 検証結果と復旧履歴を監査ログへ残す。

## 8. セキュリティ・アクセス制御

- すべての通信を HTTPS で保護する。
- ノードエージェントの認証には mTLS または同等の端末認証を用いる。
- ノードごとに個別の認証情報を発行し、失効できるようにする。
- ノードは必要なタスクと対象ファイルにのみアクセスできるようにする。
- ノードのストレージパスや内部IPなどを一般ユーザーへ公開しない。
- 管理操作と公開設定変更は監査ログへ記録する。
- ファイル名やメタデータをパス・SQL・HTMLへ直接埋め込まず、入力検証と適切なエスケープを行う。
- アーカイブ展開時はパストラバーサル、過剰展開、シンボリックリンクなどに注意する。

### 8.1 RBAC（必須）

ロールベースアクセス制御（RBAC）を必須とし、少なくとも次のユーザー種別を分離する。

| ロール                 | 主な権限                                                                                               |
| ---------------------- | ------------------------------------------------------------------------------------------------------ |
| 管理者                 | ユーザー・ロール管理、全設定、保存配置、ポリシー、配信、削除タスクを含むフルコントロール               |
| 確認担当者             | 作品・ファイル情報や規約・申請内容の確認、確認結果の記録。システム全体の設定やユーザー権限の管理は不可 |
| 閲覧者（必要に応じて） | 管理情報の参照のみ。変更操作は不可                                                                     |

- 確認担当者とフルコントロール可能な管理者は、必ず別ロールにする。
- 初期状態では最小権限を適用する。
- ロール付与・変更・剥奪を監査ログへ記録する。
- 高リスク操作（公開ポリシー変更、削除、ロール変更）は操作主体と理由を記録する。

### 8.2 ノード参加・離脱

- ノード参加の基本条件は、原則として 24 時間稼働できることとする。
- ノード離脱時、運営側がノード内のデータを確実に削除できるとは前提しない。離脱済みノードに残るデータは回収不能・削除確認不能となる可能性を許容する。
- 離脱ノードの認証情報を失効し、以後のタスク配布やアクセスを停止する。
- 中央の配置情報を更新し、残存する正常なノードから新しい保存先へ再配置する。
- 最低 2 保存先の要件を満たせない間は、該当ファイルを劣化状態として表示し、必要に応じて配信を制限する。
- 参加規約では、離脱後にノード内データが残存し得ること、運営側がその消去を保証できないことを明示する。

## 9. 配信方式

### 9.1 初期版

初期版は中央配信ゲートウェイが保存ノードからファイルを読み出し、ユーザーへ HTTPS で配信する。初期段階ではキャッシュを設けず、公開ポリシーの判定を単純に保つ。

### 9.2 将来のキャッシュ

必要に応じて Nginx 等のリバースプロキシ／キャッシュを追加できる構成にする。キャッシュ対象は公開可能と確認されたファイルだけに限定し、公開停止時の失効手順を必須とする。

## 11. 監視・運用

### 11.1 テレメトリ

- OpenTelemetry（OTel）等を利用して、メトリクス・ログ・トレースを収集する。
- Grafana に監視データを集約し、ノード、タスク、ストレージ、配信の状態を可視化する。
- 特定のメールアドレスやチャット等への通知先は初期設計では設定しない。Grafana 上で確認できるダッシュボードを基本とする。
- 通知先を後から追加できるよう、監視・通知の仕組みは分離する。

最低限、次の項目を監視する。

- 中央 API とデータベースの稼働状態
- ノードの最終応答時刻
- ノードごとの空き容量と使用量
- 保存待ち・失敗タスク数
- ハッシュ検証の不一致件数
- 2 保存先を下回るファイル数
- 配信エラー数
- 公開ポリシーの変更履歴
- 削除・公開停止申請の受付数と処理状態
- ノード削除タスクの成功・失敗状況

運営者向け画面では、未取得、未検証、保存先不足、再配布ポリシー不明、失敗タスク、未処理申請を優先して表示する。

### 11.2 中央サーバーのバックアップ

中央集権サーバーのバックアップは IaaS が提供するバックアップ機能を利用するため、バックアップ先の設計は本書の対象外とする。アプリケーション側では、バックアップの成否や復旧に必要な設定・データの依存関係を整理する。

### MVP-1：目録・アクセス制御

- 管理者によるユーザーアカウント作成
- RBAC と管理者／確認担当者の権限分離
- 作品・ファイルの登録
- `uploader.jp` の元URL、作者、説明、README・規約情報の記録
- README 等がない場合の確認・連絡フロー
- 検索と詳細表示
- CSV／JSON エクスポート
- 再配布ポリシーの管理
- 削除・公開停止申請フォーム
- 外部公開情報の提供フォーム

### MVP-2：単一ノード保全

- ノードエージェント登録
- 保存タスクの作成・実行
- SHA-256 とサイズの検証
- 自動再試行（1実行あたり最大5回）
- 管理者による `failed` タスクの手動再実行
- 再実行前のステージングデータ再検証と、必要時の正しいデータ再アップロード
- 未検証オブジェクト・部分ファイルの清掃
- 成功時のみ `verified` とし、成功後にステージング元データを削除
- 状態表示

### MVP-3：複数ノード分散配置

- A/B ノードの混合参加
- 原則 24 時間稼働を参加条件として扱う
- ファイル単位の保存先割当と最低 2 ノード保存
- 保存容量にシステム上の固定上限を設けない
- 容量と稼働状態の監視
- ノード離脱・欠損の検知と再配置
- 管理者裁量による保存優先順位付け
- 手動または優先度ベースの追加複製

MVP-3実装時の具体化：

- 新規取り込みは、容量条件を満たすオンラインノードを2台選択し、ノードごとに独立した保存タスクとステージングデータを作成する。2台を確保できない場合は、保全済みと誤認させないため取り込み要求を拒否する。
- ファイルの `preservation_status` は、オンラインでハッシュ検証済みの配置が設定された最低複製数以上ある場合に限り `verified` とする（既定値は2）。1つだけの場合は `degraded`、タスク実行中は `queued`、全配置がオフラインの場合は `missing` とする。
- 配置一覧 API は配置ごとのノード、ノード状態、検証状態、正常な複製数を管理者・確認担当者に返す。
- 追加複製は、正常な配置を持つソースノードがローカルのサイズとSHA-256を再確認して中央ステージングへ転送し、中央側でも検証した後、ターゲットノード向けの通常保存タスクへ切り替える。
- 30秒ごとの照合処理は、2分以上ハートビートがないノードをオフラインとして扱い、未検証の配置を `missing` に更新する。既に `verified` の配置は、ノード停止だけではデータ消失と断定せず検証状態を保持し、正常なソースと容量を満たす別ノードがあれば再配置タスクを作成する。
- 必要な正常レプリカ数は2とし、障害耐性のため1件の余剰レプリカを許容する。正常なレプリカが3件までは自動削除せず、4件以上の場合に余剰整理を検討する。
- 余剰整理は、対象ファイルの他のタスクが実行中でない場合に限り、1ファイルにつき同時に1件の削除タスクを作成する。削除対象はオンラインかつ `verified` の配置に限定し、対象ファイルを保持する全オンラインノードが連続5分以上オンラインであり、かつ最も新しい検証済み配置の検証時刻から5分以上経過してから削除をキューに入れる。これにより、ノード復帰直後や配置追加直後の削除を避ける。
- 物理データの削除は対象ノードのエージェントが管理ストレージキーを使って実行し、成功報告後に配置状態を `deleted` にする。失敗または結果が不確かな場合は正常な配置として数えず、監査ログに記録する。オフラインノードのデータは自動削除しない。
- ローカルComposeのA/Bノードは開発・動作確認用であり、同じ物理ホスト上の障害ドメイン分離を保証しない。実運用では別ホストまたは独立したストレージに配置する。

### MVP-4：中央配信ゲートウェイ

- 公開条件のサーバー側判定
- 中央経由のファイル配信

### MVP-5：保全強化・運用可視化

## 15. MVP-3 API・運用メモ

- `GET /api/v1/files/:id/placements`：配置ごとのノード状態、検証状態、正常な複製数を返す。
- `PATCH /api/v1/files/:id/replication`：ファイル単位の最低複製数（2–100）と複製タスク優先度（0–5）を設定する。
- `POST /api/v1/files/:id/replicate`：管理者が複製数設定を満たすためのタスク作成を要求する。必要数が満たされている、または既にタスク実行中の場合は新規タスクを重複作成しない。
- `POST /api/v1/admin/placements/reconcile`：管理者が配置照合を即時実行する。通常はAPI内のバックグラウンド処理が30秒ごとに実行する。
- `replicate` タスクはソースノードが取得し、ソースの実ファイルを検証して中央へ送信する。中央でサイズ・SHA-256を検証した後、同じタスクIDをターゲットノード向けの `store` タスクに切り替える。ターゲットの保存・再検証は通常のストレージタスクと同じ経路で行う。
- `delete` タスクは、必要数＋1を超えた余剰レプリカの物理データを対象ノードのエージェントが削除する。エージェントの成功報告を受けるまでは配置を `deleted` としない。
- ちょうど2台しか参加していない状態で片方が停止した場合、残り1台への複製だけでは障害耐性を回復できない。停止ノードが復帰するか、3台目の適格なノードが参加するまで保全状態は `degraded` となる。

## 16. URL自動収集と重複排除（実装メモ）

- 管理画面の URL自動収集では、管理者が指定した HTTPS の `uploader.jp` / `getuploader.com` 配下の開始URLから、一覧ページとページ送りを限定的に調査する。
- 1回の収集は開始URL最大10件、ページ合計最大10ページ、候補最大100件に制限する。ログイン・パスワード・CAPTCHAは自動回避しない。
- 新規候補は保全リクエストとして登録するだけで、ファイル取得・保存・一般公開は自動開始しない。
- `source_url_registry` の正規化URLを一意キーにし、公開リクエストと自動収集で共有する。既存申請・カタログ済みURLは新規申請を作成せず破棄する。
- 正規化時にホスト名を小文字化し、URL fragment と既定ポート `:443` を除去する。クエリはダウンロードトークン等の可能性があるため保持する。
